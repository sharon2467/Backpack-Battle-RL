### A. Recommended Wolpertinger231: least buffs + feedback stamina

Original `Items/Wolpertinger.gd` is21lines, extendsItem. CSV231 is Godly/Pet/Nature, ordinary neutral shop(empty), cd5, p1=0.7,p2=3,p3=15; scene binds the script and its TileMap has fourbody(tile3)/eightstar(tile4) entries. CSV demo empty plus existing ItemBook/ItemDescriptor release handling marks the normal released descriptor, not an unreleased asset. Resource presence/release Source is not a new native canAdd/instantiate result; acquisition is outside this battle scope.

Its preparation adds speed `getNumAffectedItems()*getP3()/100.0`, registers own beneficial-buff signals in preparation order, and stores `staminaRegenPerBuff=getP1()*baseStaminaRegen/100.0` with that exact arithmetic order. A cooldown picks three least buffs then activates. Each actual buff amount delta, positive or negative, changes staminaRegen by `amount*staminaRegenPerBuff` and snapshots Character Stat.StaminaRegen. Block/debuff changes are not these registered beneficial channels; failed/resisted/capped/protected zero changes must not fabricate callbacks. This is real feedback into stamina-limited weapon scheduling, not a display effect.

Original Item.getLeastStacks builds a local ordered priorStacks table, repeatedly chooses uniformly among the current minimum categories, increments its **virtual** count and aggregates pickedStacks insertion order before any real gain. Item.giveLeastBuffs then grants those aggregated amounts, preserving current logging mode and parent argument. It does **not** wrap the delayed-logging mode used by giveRandomBuffs. Caps/amplification/callback effects during grants do not retroactively recalculate its earlier picks. Preserve one source choice operation per requested unit, including singleton tie sets. Do not alias it to independent uniform random buffs or giveMostBuffs.

Reuse current _stack_picker_inputs/category mapping, existing grant/resist/protection/metrics/history, current ordered target-cache builder and central on_stack_changed. Add only the actual Pet target predicate/cache and listener feedback. This naturally mixes with already implemented Squirrel164 steals, Sapphire199 paidMana, Emerald197/Ruby64 startup buffs and a stamina-using Sword1: positive grants and actual loss/use change regen; subsequent attacks consume the resulting stamina. No new Timer class/kernel required. Source SDK stays26business Timers; a future real captured case would retain its own raw32 including inactive six, not copy current instance rows.

Proposed implementation base is exact accepted497 Source SDK15 (business family also exercised inside505's fixed029), not a modification of505captured/539adapter. Extend existing initialize_experimental_nonking/validate_experimental_nonking_layout fixed set by231, at least one experimental kind, class0/default/noKing; old formal/CLI/batch/Squirrel/King routes remain. Registration would become82, but formal count stays75. No user-provided allowlist or new initialize_wolpertinger API.
