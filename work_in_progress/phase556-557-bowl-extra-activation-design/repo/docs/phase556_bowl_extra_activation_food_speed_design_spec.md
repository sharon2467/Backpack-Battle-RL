### Extra-effect chronology, RNG, event/parent and ended boundaries

Original Item.trigger4409–4416 performs adjustCooldown once, adds iterationCooldown to triggerTime once, calls doCooldownEffect once, then **only if live doubleActivationChance>0** consumes `Util.flip`, then on success calls doCooldownEffect once more. It does not call trigger recursively, re-adjust cooldown, make a second positive roll, or gate this second call on a new ended/cooldown test. Zero chance consumes **no** double-activation primitive (unlike attackEffectCount's existing default-zero flip). Positive20% consumes one `randf`, comparing `raw<=chance`; preserve the boundary and shared stream order.

For Squirrel the actual order is first steal picker/loss/gain and queue behavior → first activate/event/metric/tooltip → its real activation-tail pitch if not limited → positive modifier flip → optional second steal/effect → second activate/pitch if not limited. No early selection, reused pitch/flip return or fake label. Both effect calls use the original default/null parent; each actual Activation allocates a separate root Activation event. The second is not a child of the first or of a newly invented Bowl event. Existing use/grant/steal parent behavior is preserved.

`Item.activate`4669–4720 limits Activation attempts to three per Util-time value before event/metric/pitch. Effects preceding activate still execute when the fourth Activation is suppressed. Thus a trigger whose first activation is the third may have a real first event/pitch, then roll positive, execute the second business effect, and suppress its fourth Activation/pitch. The limiter does not cancel the extra effect or its preceding picker. When ended, existing activate suppresses event/metrics but still reaches Squirrel pitch for attempts within the limit; fourth+ returns before pitch. The Item.trigger wrapper itself adds no fightEnded guard. First/second effect helpers retain existing ended/queue handling. Natural occurrence of such boundaries is not promised; explicit already-ended/same-frame unit prestates can test them without claiming Native hits.

In particular, if the **first** activation attempt is already fourth/limited, doCooldownEffect still returns normally, so a live positive chance still consumes the extra roll and may run the second effect (whose activation is fifth/limited). Only chance0 skips that roll. Activation returning no event is not a cancellation result for Item.trigger. Do not interpret a missing Activation event/pitch as proof that no effect or extra-chance draw occurred.

For Wolpertinger each effect is existing least3 grants then activate; resulting own beneficial callbacks update live stamina regen/history through the accepted231 path. Extra effect repeats this whole actual effect, not merely an Activation metric. Existing global event_num/delayed-history and grant semantics remain authoritative. ### Food speed ledger and serialization

Bowl has real instance `speedBonusGiven=0.0`, reset0.0 by onPrepare. Each doCooldownEffect first performs existing giveRandomBuffs2. If the ledger is below100, for **each** affected Food it computes `min(25,100-speedBonusGiven)` against the unchanged pre-loop ledger and calls item.addSpeed(curBonus/100). Only after the whole target loop it increments `speedBonusGiven += 25`, even when that target list is empty. At/above100 it skips Food speed/ledger progression but still gives buffs and activates. It does not increment per target, clamp the ledger, skip full caller at cap, or give speed to Pets/Sword by the global predicate. Source snapshot inclusion is sufficient for this block; a future Native collector subtype/INPUT/comparator extension for Bowl would be a separate task.
